## 为什么要把内核当操作系统来构建

Corevo 的 `ReactAgent` 当时已经是一个近 80 KB 的单文件：内核循环、工具调度、上下文压缩、流式输出、子 Agent 管理全部缠在一起。我们不是没有抽象——`BaseLLM`、`ConfigProvider`、`AgentMiddleware` 都有——但**核心循环本身不可替换**：想从自研 ReAct 换成 LangGraph 或 PlanAct，想给某个租户换一套记忆实现，都要动主循环。全局单例的 ToolRegistry 则让多租户隔离变成了打地鼠。

在白板上推演架构时，我写下了一个后来成为整个设计纲领的判断：

> 不是精简出一个薄核心，而是把整个 Agent 系统的每一层全部做成可替换的插件。**没有特权内核**——LLM、工具、Session、沙箱、Agent Loop 都是地位平等的插件，可以在配置中替换或卸载。

这就是 Agent OS 的核心隐喻：操作系统的内核不实现文件系统、不实现网络协议栈，它只负责进程调度、生命周期和系统调用约定。对应到 Corevo，内核的职责被压缩到三件事——插件的加载与卸载、依赖管理、副作用追踪；真正的 Agent 能力全部由插件贡献。

## 平等的插件：协议接口与乐高组装

落地形态是一张模块职责矩阵。每个模块都是一个 Protocol 接口，内核只认契约不认实现：

| 模块 | 职责 | 可替换实现示例 |
|------|------|---------------|
| Kernel | 驱动 think → act → observe 循环 | ReAct / LangGraph / PlanAct |
| LLM | 统一模型调用 | Anthropic / OpenAI / DeepSeek / Ollama |
| Tool | 注册、发现、执行 | 内置注册表 / MCP / 延迟加载注册表 |
| Memory | 跨会话记忆存取 | 文件记忆 / 向量记忆 / Mem0 |
| Storage | 文件读写与路径抽象 | 本地 / MinIO / 虚拟路径 |
| Sandbox | 隔离执行不可信代码 | 进程级 / Docker / gVisor |
| Compression | 上下文窗口管理 | 三层压缩 / 摘要 / 滑动窗口 |

组装发生在 `AgentRuntime` 这个"乐高底座"上。本地开发时一个最小运行时只要三个参数；SaaS 生产环境则换上数据库驱动的 LLM 工厂、按租户解析的工具注册表、MinIO 存储、Docker 沙箱和一串中间件；想试验新循环策略，把 `kernel=ReactKernel()` 换成 `kernel=LangGraphKernel()` 即可，其余插件原样复用。我们在评估 DeerFlow 时就是靠这套接口做"择优融合"：工具的延迟加载、自动记忆提取、虚拟路径直接以插件形式接入，而自研的三层压缩和过渡性声明检测原地保留。

## Checkpoint：进程快照与跨节点迁移

插件化解决了"能力怎么换"，无状态化解决的是"进程可以在哪跑"。内核当时的对话上下文活在进程内存里，Pod 一重启全部丢失——这等于进程无法迁移，K8s 的水平扩缩形同虚设。

我的方案像 OS 的进程快照：每轮 LLM 调用结束后，把完整的消息数组和压缩状态序列化为一份 checkpoint，异步 UPSERT 进 PostgreSQL——同一会话永远只有一行最新快照，不保留历史链表；Pod 漂移后由新 Pod 在 WebSocket 重连时 `load()` 恢复上下文，对话无缝继续。研究过 LangGraph 的四表加 blob 分离设计后，我刻意没有照搬：它的时间旅行和 human-in-the-loop 中断恢复我们现阶段用不上，单表 JSON 列加 JSON 序列化（而非有安全风险的 pickle）已经足够，每会话十几 KB、百并发也就几 MB。

真正的硬骨头是快照之外的**有状态组件盘点**。运行中的任务是 asyncio 协程——协程不可序列化，这是 Python 的本质限制。所以 TaskManager 的无状态化不是"把状态搬走"，而是"让任务能在另一个 Pod 上重生"：状态统一入库，用户重连时新 Pod 检测到"数据库里有 running 任务但本机内存没有"，就从 checkpoint 恢复上下文重新拉起。对执行到一半的子 Agent，我们甚至不假装能续跑——给 LLM 注入一条合成的中断提示"此任务因服务重启而中断，如需要请重新执行"，让模型自己决策，三十行代码解决了本来要分布式锁加心跳的方案。

## 模型可见即已记录：日志是唯一真源

操作系统有系统调用追踪，Agent OS 的对应物是我坚持的日志不变量：

> **模型看到的任何上下文，都必须能从仅追加的会话事件日志中重建。** 不存在"隐形上下文"——任何进入模型请求的内容，都必须先成为日志中的一个事件。

传统框架里 `messages[]` 是内存中的可变状态，日志只是旁路 tracing，出问题时你既无法回放也无法追责。把关系反过来之后——日志是唯一事实源，模型看到的历史只是日志的纯函数投影——可观测性、可恢复性、可审计性就成了同一个机制的三个侧面。配合租户审计日志（谁在何时发布了什么 Skill）与执行侧的结构化事件流，整个系统第一次变得"可回放"。

## OS 化带来了什么，又没带来什么

这套构建方式最直接的回报是演进能力：新模型提供商、新循环策略、新沙箱引擎都变成了"再写一个插件"，而不是"再改一次主循环"。但它也有诚实的边界。插件化不等于免费——每个 Protocol 接口都是一份要长期维护的契约，接口切错地方的代价比耦合更高；checkpoint 恢复的是上下文而不是执行现场，被中断的子 Agent 只能重做；浏览器会话、Python REPL 命名空间这类"活的对象"本质上不可序列化，最终只能接受丢失、优雅降级，像 Jupyter 重启丢内核状态一样。

> 我逐渐相信：Agent 系统的护城河不在某个聪明的 prompt 或循环策略里，而在这些"无聊"的操作系统品质里——隔离、快照、可回放、可替换。模型每半年换一代，而内核要活过很多代模型。
