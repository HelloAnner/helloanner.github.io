## 为什么需要子智能体

单个 Agent 有两个绕不开的天花板：**上下文有限**和**不能并行**。

第一个问题在工具数量膨胀后尤其尖锐。内核内置工具超过 90 个，如果全量注入每轮 LLM 调用，模型面对的是一个几十项的菜单，选错工具的概率显著上升。我们当时没有运行时动态路由工具的能力，子智能体其实是一种架构补偿——把任务拆给多个专注的 Agent，每个只挂少量工具，准确率自然回升。代价是你得提前把任务分解清楚，对模糊任务无效。

第二个问题更本质：主 Agent 的 ReAct 循环是串行的，而很多真实任务天然可并行——同时研究两个竞品、同时跑三路数据核查。子智能体给出的答案是：为主 Agent 提供一个 `task` 工具，调用它就派生一个全新的 ReactAgent 实例，有自己的 messages 列表、自己的工具集、自己的 system prompt，主 Agent 的对话历史一个字节都不会传进去。本质上是**上下文隔离 + 并发执行**。

## 能力的三个层级：Tool、Skill、SubAgent

在 Moss 里，子智能体不是孤立的设计，而是扩展体系的最高一层。三层之间是清晰的递进关系：

```text
Tool      能力的最小单元：无决策、无记忆，入参 → 出参
  ↓ 打包
Skill     能力 + 方法论：SKILL.md 指令 + scripts/ + references/，
          由主 Agent 按需渐进加载
  ↓ 人格化
SubAgent  独立的协作者：完整 ReactAgent 实例，
          独立上下文 / 独立工具集 / 独立提示词
```

三层共享同一种哲学：**文件系统即配置**。一个子智能体就是一个目录里的 `agent.md`，用 YAML frontmatter 声明自己：

```markdown
---
name: code-reviewer
description: Expert code reviewer
tools: Read, Grep, Glob, Bash
disallowedTools: Write, Edit
max_iterations: 10
---

You are a professional code reviewer...
```

`SubAgentRegistry` 负责扫描与解析，加载目录可以多层叠加：内核内置 → 租户级 → Agent 级，后注册覆盖先注册。新增一个子智能体不需要写注册代码、不需要重启服务，把目录放到 `subagents/` 下即可。这套"零代码扩展"让子智能体和 Tool、Skill 一样，成为可以被版本管理、被环境间搬运的普通资产。

## 三种身份：分身、专家与伙伴

第一版设计里我们踩过的最大坑，是把"子智能体"当成单一概念。实际上它是三种不同协作关系的统称：

| 产品名 | 代码标识 | 触发方式 | 能力来源 |
|--------|----------|----------|----------|
| 分身 | `derived` | `agent="self"` 或未指定 | 继承当前主 Agent 的角色与能力绑定，再移除安全敏感工具 |
| 专家 | `professional` | `subagent="名称"` | 来自注册中心已发布的记录，显式空工具就是真的无工具 |
| 伙伴 | `main` | `agent="名称"` | 取另一个主 Agent 的角色与能力，不继承调用方任何资产 |

三种身份的边界体现在细节上。分身的存在意义是"让我自己并行起来"，所以继承天经地义；专家的能力完全来自数据库发布配置，早期版本曾给空工具的专家"贴心地"补上文件工具，结果一个声称只做舆情摘要的专家突然拥有了写文件能力——违背最小权限，后来改成显式空就是空；伙伴是委派给另一个主 Agent，但绝不共享对方正在运行的会话，否则两边串线，也不符合"子任务"的语义。

触发方式也一起改了。旧做法是在 Prompt 里写"复杂任务才委派""风险问题交给风险伙伴"，结果模型把"帮我查一下"都当成委派信号，误触发大量无意义的子任务。新做法把选择权完整交还给模型：`task` 工具的参数里显式指定身份，未指定时稳定兜底为 `agent="self"`，各 Agent 的 Prompt 只描述自己的领域边界，不做路由规则。

## 创建即冻结：数据库驱动的执行单元

子智能体设计的核心转变，是它从"Prompt 里的角色"变成了**数据库驱动的独立执行单元**。一句话概括链路：模型调用 `task`，任务写入 PostgreSQL；任意 Worker 从数据库领取、执行、把结果写回；文件经 MinIO 交付。

为什么必须是数据库？早期版本让内核从本地代码和配置里拼子智能体的权限，结果平台管理员在后台关了某个工具，内核可能因为本地缓存仍然暴露给模型——双事实源永远会对不上。收敛后的原则是：控制面（发布配置）和运行面（这次实际执行了什么）全部落库，内核只消费数据库返回的最终集合。

`创建即冻结` 是其中我最坚持的一条：子任务创建时，最终生效的提示词、工具集、技能集、结果 Schema、模型配置全部写入 `agent_run_snapshot`，之后的任何配置变更、调试模板覆盖都不影响已创建的任务。提示词的组成也很有讲究——子智能体**不复制**主 Agent 的 `system_prompt`，因为那里写着主 Agent 的身份和方法论（"你是风险洞察专家""遇到复杂任务就委派"），原样塞进去会让子智能体角色错乱甚至再次尝试委派。每个 Agent 需要单独发布一个 `delegation_prompt_overlay`，专门描述"被委派时你是谁、能做什么、不能做什么"。

```json
{
  "run_id": "run_child_01",
  "identity_snapshot": { "agent_kind": "professional" },
  "tool_policy_snapshot": { "effective": ["web_search", "read", "write"] },
  "max_iterations": 20,
  "snapshot_hash": "sha256:..."
}
```

冻结之后，执行就可以脱离创建者了。Worker 用 PostgreSQL 的 `FOR UPDATE SKIP LOCKED` 原子领取任务，靠心跳续约租约，靠单调递增的 Fencing Token 阻止旧执行者在恢复后重复提交，靠加密 Checkpoint 在换 Pod 后恢复消息与状态。这样即使创建任务的 Pod 整个消失，任务也会在其他 Worker 上跑到终态。

## 上下文交接、结果交付与租户边界

上下文传递遵循一条铁律：**显式交接，绝不自动继承**。父 Agent 的聊天历史、记忆不会传给子智能体，必须在 `task` 的 `context` 参数里写清楚主体、已确认事实、来源、约束和期望输出。这个设计消灭了一整类"我以为它知道"的 bug。文件则走另一条隐式通道：子智能体继承 session 语义，产物写到 MinIO 并通过 `file_session_refs` 给父会话建立引用——父会话看到的是带权限校验的"文件事实"，而不是某台机器的本地路径，跨 Pod 也能读。

结果协议采用**稳定外壳 + 开放正文**：`result_outcome`、`quality_state`、`summary`、`evidence`、`artifacts`、`limitations` 这些字段每个任务都一样，让父 Agent 和前端知道任务完成度与质量；`data` 里面装什么完全开放，由任务性质决定。超长结果不硬截断，而是归档为文件、内联只留摘要和指针。

多租户下，子智能体资产走和工具相同的隔离路径：`TenantAssetResolver` 每请求解析出当前租户可见的子智能体集合（平台内置 + 租户自定义 + 同租户伙伴 Agent），全局 Registry 保持只读。安全边界收敛为三重交集——**身份授权 ∩ 运行时 Profile ∩ Worker 安全实现**，子智能体不能递归委派、不能动态搜索工具、不能执行 Shell 和浏览器。另有一个全局开关 `admission.accept_new_delegations` 作为总闸：关闭时新委派在网关被拒绝，但已创建的任务继续跑到终态，历史数据不动。

> 这一章的教训可以收成一句：委派系统的正确性不来自模型守规矩，而来自"创建即冻结 + 数据库事实源 + 显式上下文"这三道墙。模型可以犯错，墙不会。
