## 从"拖报表"到"问数据"：为什么 BI 需要 Agent 平台

帆软的主业是 BI。过去十几年，用户分析数据的方式是拖拖拽拽做报表；而大模型出现后，最自然的诉求变成了直接"问数据"——帮我分析一下这个月的销售、对比一下两个区域的毛利、把结论做成一份报告。

这类任务和普通的聊天机器人有本质区别：它是**多步骤、需要工具的**。取数要查数据集，清洗要写代码，出图要执行脚本，结论要交叉核验。一个 Agent 要完成它，就得具备 ReAct 式的"思考—调用工具—观察—再思考"循环，还要能读文件、跑代码、调用业务接口。而当这样的能力要交付给企业客户时，问题立刻从"模型聪不聪明"变成了平台问题：权限怎么管、租户怎么隔离、计费怎么算、客户自定义的能力怎么安全地跑起来。

Moss 就是为回答这些问题而生的。它不是一个聊天框，而是一套企业级 Agent 平台：向下管理算力、模型与沙箱，向上支撑数据分析、客户洞察、风险洞察这类业务 Agent。

## 平台、内核、沙箱：三层各管一件事

Moss 在部署上是清晰的三层结构，控制面与数据面分离：

```text
┌─────────────────────────────────────────────────────────┐
│                  Frontend (React 18)                     │
└────────────┬───────────────────────┬────────────────────┘
             │ HTTP (控制面)          │ WebSocket (数据面)
             ▼                       ▼
┌────────────────────────┐  ┌─────────────────────────────┐
│  平台层 fineinsight     │  │  内核层 Corevo (Moss Kernel) │
│  Java / Spring Boot    │  │  Python / FastAPI + Uvicorn │
│  - 用户认证 / RBAC     │  │  - ReactAgent 执行引擎      │
│  - 租户隔离 / 计费配额 │  │  - Tool / Skill / SubAgent  │
│  - 会话元数据 / 调度   │  │  - LLM 路由（多家 Provider）│
└────────────┬───────────┘  │  - WebSocket 实时流         │
             │              └──────────────┬──────────────┘
             │                    spawn（按需）│
             │                             ▼
             │              ┌─────────────────────────────┐
             │              │  沙箱层 sandbox-runtime      │
             │              │  轻量容器，执行租户自定义代码 │
             │              │  生命周期 = 单次任务          │
             │              └─────────────────────────────┘
             ▼
   PostgreSQL / Redis / RabbitMQ / MinIO
```

这个分层回答了一个关键问题：**内核不做身份认证，只消费已被平台认证过的上下文**。登录、鉴权、限流、计费这些"企业级"职责全部在 Java 平台层；Python 内核只关心一件事——把 Agent 的推理循环跑好。两者通过 HTTP/WebSocket 通信，内核侧有一个 `ConfigProvider` 抽象层，当平台接管配置管理时只需替换实现，这是内核可以脱离平台独立运行的关键。

沙箱层的动机则来自安全：租户可以上传自定义的 Tool 和 Skill 脚本，这些代码绝不能在主进程里裸跑。每次执行按需 spawn 一个秒级生命周期的容器，执行完即销毁。

## 自研 ReAct 内核：不依赖 LangChain 的取舍

内核的核心是一个完全自研的 `ReactAgent`，不依赖 LangChain / LangGraph。这是我们做的第一个重要取舍。

原因很直接：在生产环境里，框架的抽象层往往是负担而非助力。我们需要对推理循环有完全的控制权——实时流式回调、三层上下文压缩、按迭代的细粒度事件，这些都要求循环的每一步是可观察、可干预的。自己实现 ReAct 循环后，这些能力变得很自然：

```python
class ReactAgent:
    def __init__(
        self,
        llm: BaseLLM,
        max_iterations: int = 100,
        tools: list[str] | None = None,        # 过滤可用工具
        tool_registry: ToolRegistry | None = None,
        skill_registry: SkillRegistry | None = None,
        callbacks: AgentCallbacks | None = None,  # 实时回调
        stream_mode: str = "full",              # none | chat_only | full
        is_subagent: bool = False,              # 子 Agent 标记
        tenant_id: str | None = None,           # SaaS 租户标识
        ...
    )
```

有两个设计我至今认为是做对了的。一是**回调系统把执行引擎和传输层解耦**：ReactAgent 从不直接操作 WebSocket，只是发出 `on_thinking`、`on_tool_call`、`on_response` 这类事件，由上层 Handler 映射成 WebSocket 消息帧。三种流模式（`none` / `chat_only` / `full`）让调用方自由选择要多少实时性。二是**文件系统即配置**：一个 Agent 就是一个目录——`config.yaml` 定义身份，`agents.md` 定义人设，`skills/`、`subagents/`、`tools/` 是它的能力，新增能力不需要写注册代码、不需要数据库迁移，放一个目录进去就会被自动发现，天然支持版本控制与环境间迁移。

当然自研也有代价，我在工程化复盘里如实记过：工具执行是严格串行的，浪费了 LLM 一次返回多个独立 tool_call 时的并发能力；回调是被动通知而非可拦截的管道，横切关注点（限流、审计）只能散在主循环的 if 分支里。这些是当时为了把核心循环跑稳而欠下的债，后续章节会谈到部分补救。

## Tool、Skill、SubAgent：三层扩展体系

Moss 的扩展能力分三层，抽象程度逐级递增：

| 层级 | 本质 | 形态 | 决策能力 |
|------|------|------|----------|
| Tool | 能力的最小单元 | 一个 Python 函数（`@tool` 装饰器或类继承） | 无，入参 → 出参 |
| Skill | 打包的能力与知识 | `SKILL.md` + scripts/ + references/ 目录 | 靠主 Agent 渐进加载 |
| SubAgent | 独立的协作单元 | 一个完整的 ReactAgent 实例 | 有，独立推理循环 |

Tool 没有决策逻辑、没有上下文记忆，内核内置了 90+ 个——文件操作、bash、网络搜索、代码执行、业务查询等，启动时由 `ToolRegistry` 自动扫描发现，参数 Schema 直接从 Python 类型注解推导成 OpenAI function calling 格式。Skill 解决的是"工具会用了，但不知道业务方法论"的问题：一个 Excel 数据分析 Skill 会带着自己的脚本、参考文档和触发词，按需注入上下文。SubAgent 则是一次真正的委派——主 Agent 通过 `task` 工具派生一个拥有独立上下文窗口、独立工具集、独立 system prompt 的新 Agent。

三层共享同一套优先级语义：**内置级 < 租户级 < Agent 级，后注册覆盖先注册**，覆盖关系清晰可查。

## 从单机到 SaaS：多租户改造的动机

Moss 最初是单机单进程：全局单例的 `ToolRegistry`、本地文件系统、没有租户概念。这在 POC 阶段没问题，但要变成一个服务多家企业的 SaaS 产品，几乎所有假设都要推翻。

核心矛盾在于：租户隔离如果靠容器（每租户独占 Pod），小租户也要常驻资源，成本无法接受；所以阶段一选择了**多租户共享 Pod**——所有租户的请求混跑在 2-3 个 Agent 内核 Pod 里，隔离完全靠代码实现。这条隔离链路由四个环节组成：

1. **TenantContext**：请求入口用 `contextvars` 注入租户身份，整条链路任何代码都能拿到，无需层层传参；
2. **TenantAssetResolver**：每请求解析该租户可见的 Tool/Skill/SubAgent，替代全局单例 Registry，杜绝跨租户泄漏；
3. **StorageProvider**：所有文件路径强制带租户前缀，本地磁盘与 MinIO 对象存储可切换；
4. **沙箱 Job 隔离**：自定义代码在独立容器执行，`job_id` 而非 `tenant_id` 是最小隔离单元。

演进路径被规划为三阶段：阶段 0 单机开发态；阶段 1 多租户共享 Pod + 对象存储，支撑几十个租户；阶段 2 混合模式——普通租户共享池，大客户独占 Pod，沙箱升级到 gVisor/Firecracker 级隔离。最小运行单元被重新定义为 **Session = 租户级 Agent 定义 + 用户级上下文**，运行结果归属用户，存储在 `sessions/{tid}/{aid}/{sid}/` 下。

> 回头看，这轮改造最大的教训是：无状态化的成本几乎总被低估。"状态边界"的划分必须极其精确，稍有不慎就会在用户可见的地方暴露不一致——我们为此付过好几次线上事故的学费。

本章给出了 Moss 的全景：为什么存在、怎么分层、内核与扩展体系的设计取向。这本书的后面三章各挑一条主线深入。**第 2 章讲子智能体**——三层扩展体系里最复杂的一层，以及它如何从"Prompt 里的角色"演进成数据库驱动的独立执行单元；**第 3 章讲沙箱文件系统**——当执行环境不再是本地磁盘，我们如何用三段式执行模型重建"文件就在原地"这个前提；**第 4 章讲 Agent OS**——当工具、技能、记忆、租户、调度全部就位后，平台层如何把它们组装成一个可运营的操作系统。
